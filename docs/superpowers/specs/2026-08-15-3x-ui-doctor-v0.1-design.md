# 3x-ui Doctor v0.1 Design

## Product contract

3x-ui Doctor is an unofficial, read-only-first companion CLI for preflight,
audit, and regression checks against 3x-ui panels. Version 0.1 guarantees the
v3.5.0 to v3.6.0 upgrade path and daily checks against v3.6.0. Other panel
versions run only version-independent checks and produce an `INCONCLUSIVE`
readiness result.

`READY` means that Doctor found no known blocker in the evidence it collected.
It is not a guarantee that an upgrade is risk free. Missing required evidence
must never be treated as success.

The project is a clean-room implementation that consumes documented HTTP APIs.
It does not copy, modify, link, or embed 3x-ui source code.

## Scope

Version 0.1 provides:

- a Go CLI and non-root Docker image;
- `preflight`, `verify`, and `check` commands;
- authenticated collection from one master and all explicitly configured
  direct child panels;
- normalized, HMAC-redacted snapshots and before/after diffs;
- deterministic subscription sampling and round-trip parsing;
- 60-second multi-node traffic observation;
- twelve built-in, read-only rules; and
- terminal, JSON, and Markdown reports.

It does not provide a web UI, local host agent, direct database or log access,
automatic repair, notifications, third-party rule packs, or generic support for
all 3.x releases.

## CLI contract

```text
xui-doctor preflight --config doctor.yaml --target v3.6.0 --baseline-out before.json
xui-doctor verify    --config doctor.yaml --baseline before.json
xui-doctor check     --config doctor.yaml
```

All commands accept `--format terminal|json|markdown`, `--output <path|->`,
`--observe 60s`, and `--force`. A `stable` target is resolved to a concrete
version before collection begins and that version is recorded in the run
manifest. Failure to resolve it is an initialization error.

Exit codes are:

- `0`: `READY`, including results containing warnings;
- `1`: `BLOCKED`, at least one blocking rule failed;
- `2`: `INCONCLUSIVE`, no blocker was found but required evidence is missing;
- `3`: invalid input, configuration, secret loading, or output initialization.

If blockers and incomplete evidence coexist, the aggregate state is
`BLOCKED`, while every inconclusive rule remains visible in the report.

## Configuration

`doctor.yaml` is versioned with `schema_version: 1`. It contains:

- `panels`: a stable local ID, `master` or `node` role, HTTPS URL, token
  environment-variable name, expected panel GUID, and each node's master-side
  GUID;
- `redaction`: HMAC key environment-variable name and a non-secret key ID;
- `subscription.sample_cap`, default 50;
- `traffic.relative_threshold`, default 0.05;
- `traffic.absolute_threshold_bytes`, default 67108864;
- `traffic.limit_grace`, default 30 seconds;
- `transport`: 10-second request timeout, at most four panels and two requests
  per panel in flight, TLS verification or an optional SHA-256 certificate pin,
  and an optional proxy URL environment-variable name;
- `transport.allowed_redirect_hosts`; and
- `report.include_network_identifiers`, default false.

Tokens, HMAC keys, and proxy credentials cannot be embedded in YAML. TLS
verification cannot be disabled. Network access is direct unless an explicit
proxy environment-variable reference is configured.

## Architecture and data flow

The implementation uses typed v3.5 and v3.6 adapters. Live OpenAPI documents
are data for contract and drift checks; they never generate executable clients
at runtime.

1. Parse configuration, load secrets, resolve the target, and freeze a run
   manifest containing Doctor and rule-pack versions, panel identities, panel
   and Xray versions, OpenAPI hashes, timestamps, and sampling parameters.
2. Fetch the master topology and match every direct node by GUID. Missing
   credentials, unknown nodes, duplicate GUIDs, and identity mismatches become
   explicit findings instead of silent omissions.
3. Collect only allowlisted, behaviorally read-only API endpoints. No save,
   restart, install, update, reset, import, or delete endpoint is callable.
4. Normalize API objects and generated Xray configuration into an internal
   model. Raw response bodies remain in memory only.
5. Replace sensitive identifiers with
   `HMAC(key, panel_guid + object_type + stable_id)`. Persist only aliases and
   the configured key ID.
6. Deterministically choose subscription samples across protocol, transport,
   security, inbound, and node strata. Parse bounded bodies in memory and
   discard them immediately.
7. Collect six traffic observations at ten-second intervals by default.
8. Run pure rules over normalized evidence, compare snapshots for `verify`, and
   render all formats from one result model.

An online master-side node without a corresponding configured Doctor credential
makes the complete multi-node audit inconclusive. Node assignments are compared
using the master's configured synchronization scope; nodes are not assumed to
contain the complete master object set.

## Rules

Every finding carries a rule ID, `PASS`, `WARN`, `FAIL`, or `INCONCLUSIVE`
status, anonymous subject, expected and observed values, evidence source,
impact, and remediation. Raw response fragments are prohibited.

- `API-001`: a safe read response is unexpectedly empty, has an incompatible
  media type, or violates its documented response envelope/schema.
- `API-003`: the target or post-upgrade OpenAPI removes or incompatibly changes
  a Doctor-required endpoint. Unrelated public API changes are warnings.
- `CFG-001`: a fallback cannot resolve to a valid target under v3.6 semantics.
  An empty `dest` is valid when it resolves to the child inbound's listener.
- `CFG-002`: protocol, transport, security, flow, or related fields form an
  incomplete or unsupported v3.6 combination.
- `CFG-003`: saved API state and generated Xray configuration differ in a
  connection-relevant object or field.
- `SUB-001`: sampled Base64, share URI, JSON, or Clash YAML cannot be decoded
  and parsed again.
- `SUB-003`: panel share and subscription outputs for the same anonymous client
  disagree on connection-relevant fields. Display names, ordering, and
  permitted format-only differences are ignored.
- `NODE-001`: a required node is unreachable, has the wrong identity, or does
  not reach the target panel/Xray version during verification. Reachability
  failures are inconclusive; proven identity or version mismatches fail.
- `NODE-003`: an assigned inbound or client set differs unexpectedly between
  master and node.
- `TRAFFIC-001`: for at least three consecutive intervals, the master receives
  approximately the same positive delta while the corresponding source node
  counter remains unchanged.
- `TRAFFIC-002`: corresponding master and node counters differ for three
  consecutive samples by more than `max(5%, 64 MiB)` by default. A single
  threshold crossing is a warning.
- `LIMIT-001`: a quota-exhausted or expired client remains enabled for three
  samples beyond the 30-second default grace period. API-only mode does not
  claim that an actual network connection was proven usable.

Unknown configuration semantics produce `INCONCLUSIVE`, never `PASS`.

## Security model

Panel API tokens, session material, client credentials, subscription IDs,
private keys, and database connection strings are secrets. Logs record only an
anonymous panel ID, HTTP method, path template, status, latency, body length,
and body hash. They never record headers, cookies, complete URLs, queries, raw
bodies, or panic values derived from bodies.

HTTP redirects are limited to three and same-origin by default. Cross-origin
subscription redirects require an allowed host. Authorization is never sent to
subscription origins or redirect targets. The client accesses only configured
panels and allowlisted subscription origins.

Output creation is non-overwriting unless `--force` is given. Snapshot and
report files must be owner-only. If the platform cannot establish safe output
permissions, file output fails closed. Reports containing opted-in network
identifiers are marked sensitive.

Target compatibility schemas and rules ship with the binary. Runtime code and
rules are not downloaded. Online `stable` resolution reads release metadata
only.

## Verification and release acceptance

Tests cover typed adapters, normalization, HMAC behavior, diffs, all rules,
subscription formats, malformed-input fuzz cases, safe redirect behavior,
schema drift, timeouts, identity mismatches, multi-node assignments, traffic
anomalies, and quota grace periods.

An isolated end-to-end suite snapshots a representative v3.5.0 master/node
topology, upgrades the same data to v3.6.0, and verifies expected exit states.
A 10,000-client, four-node fixture proves the sample cap and concurrency bounds
without a fixed wall-clock assertion. Security tests scan every report and log
for seeded tokens, UUIDs, emails, subscription IDs, private keys, domains, and
IP addresses.

Release gates are unit and integration tests, race detection, fuzz smoke,
static analysis, vulnerability scanning, Linux amd64/arm64 builds, and a
non-root Docker smoke test. Releases publish checksums, an SBOM, and the image
digest.
